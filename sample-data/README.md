# Sample data -- provenance and disclaimer

**Everything in this directory is entirely fictitious and synthetic.** There
is no real LNG plant, no real equipment, no real sensor data, no real
maintenance manual, and no real incident report anywhere in this
repository. Nothing here should be interpreted as describing, or
attributed to, any actual operating facility, vendor, or equipment
manufacturer.

The fictitious facility referenced throughout this repo is "Northgate Point
LNG Terminal" -- an invented name for demo purposes only.

## `sensor_readings.csv`

A synthetic hourly time series (30 days, 2026-08-17T00:00Z through
2026-09-15T23:00Z, 720 hourly readings per tag, 3,600 rows total across 5
tags) generated by a small deterministic script (fixed random seed) that is
not itself part of the shipped repo. Three realistic anomaly patterns were
deliberately injected so the deterministic anomaly-detection logic in
`backend/app/graph/nodes.py` / `backend/app/tools/anomaly_detection.py` has
real signal to find, and so the frontend's time-series chart has something
worth highlighting:

| Tag | Pattern injected | Window (UTC) |
| --- | --- | --- |
| `C-201-DISCH-PRESS` | Slow upward **drift** toward the high alarm threshold (905 -> ~980 psig) | 2026-09-11T00:00Z -> 2026-09-15T23:00Z |
| `E-101-DELTA-T` | Sudden **spike** (4.2 -> ~11 degC) that partially decays back over ~10 hours | 2026-08-31T00:00Z -> ~2026-08-31T12:00Z |
| `P-401-VIB` | Sensor goes **flat/stuck** at a plausible-looking value (2.75 mm/s, zero variance) | 2026-09-05T00:00Z -> 2026-09-06T05:00Z |
| `BOG-FLOW-301` | No injected anomaly -- a healthy "control" tag with normal diurnal variation | n/a |
| `T-101-PRESS` | A brief, benign pressure bump consistent with a scheduled boil-off vent | 2026-08-25T08:00Z -> ~2026-08-25T10:00Z |

The backend loads this CSV into the Postgres `sensor_readings` table at
startup (`backend/scripts/seed_readings.py`) -- the time series lives in
Postgres, not just the CSV, per the tutorial's "run-history in Postgres"
convention.

## `equipment/*.json`

5 fictitious sensor tag / equipment records (tag id, unit, equipment id and
name, description, and the configured normal/critical thresholds used by
the deterministic anomaly-detection logic). Loaded into the `sensor_tags`
table by `backend/scripts/seed_tags.py`.

## `manuals/*.txt`

5 synthetic equipment maintenance-manual/troubleshooting excerpts, one per
piece of equipment, written in the style of an industrial O&M manual
(possible causes, discriminating checks, and a recommended response
procedure). Each ends with an explicit "decision-support guidance only, a
qualified engineer must confirm root cause" disclaimer. These are embedded
into a local **Milvus Lite** collection and semantically searched by the
`investigate` graph node.

## `incidents/*.txt`

3 synthetic past incident/work-order reports describing fictitious prior
events at "Northgate Point LNG Terminal" that mirror the three injected
anomaly patterns above (a discharge-pressure drift, a temperature spike,
and a stuck vibration sensor), including a fictitious root cause,
resolution, and lessons learned. These are embedded into the same Milvus
Lite collection so the copilot can cite "similar past incident" precedent
alongside manual guidance, with the same disclaimer.

## Parsing format

`manuals/` and `incidents/` files share one simple, human-readable plain
text format, parsed by `backend/app/tools/knowledge_documents.py`:

```
TITLE: <title>
EQUIPMENT_ID: <fictitious equipment id>
EQUIPMENT_NAME: <fictitious equipment name>
DOC_TYPE: manual | incident

<one or more paragraphs of body text, blank-line separated>
```

Each blank-line-separated paragraph becomes one embeddable chunk, tagged
with its source document's title, equipment id, and doc type, so retrieved
results can cite exactly which manual section or incident report they came
from.

## Why this matters for the demo

Every "processed anomaly event" you see out of the box (the seeded example
work orders, and anything you trigger yourself from the bundled sample
readings) is built entirely from this fictitious data. That is what makes
this a safe, zero-setup, portfolio-shareable demo: no real plant, vendor,
or incident data is involved anywhere.
